# Eyes v0.2 durable dedup design

Status: proposed
Date: 2026-09-13
Decision: store queue state in a private Slack List

## Decision

Use one private Slack List named `Eyes queue state`. Record its fixed list ID in
the deployed skill.

This keeps message excerpts and channel metadata inside the Slack workspace.
Brian can open the list and correct state by hand. The Slack MCP connection
already required by `eyes` can read and write it, so v0.2 does not add another
credential.

The cost is API volume. The current MCP tools add or update one row per call.
There is no all-or-nothing batch upsert. v0.2 treats the post-DM writes as one
bounded write phase, retries rows separately, and never claims that the phase is
transactional.

## Options considered

| Store | Durability across runs | Setup | Cost per run | Brian can inspect it | Read/write latency | Ceiling | Concurrent access |
|---|---|---|---|---|---|---|---|
| Slack List | Independent of the Cloud Agent VM. Subject to Slack retention and Lists remaining enabled. | Create one private list, save its ID, and add list tools to preflight. Slack is already connected. | One paginated read, up to 20 row writes, and an optional verification read. No direct monetary cost. | Best. It is a normal list in Slack with filters and editable fields. | Highest of the three. Reads return at most 100 rows. Writes are one record per MCP call. | Use 100,000 rows as a planning ceiling, not a verified API contract. The design below keeps the working set under 250 rows. | Each row update is atomic, and partial updates avoid unrelated field loss. The list has no unique constraint or multi-row transaction, so concurrent inserts can duplicate a permalink. |
| GitHub Gist | Independent of the VM and versioned. | Create a Gist, save its ID, and provide a GitHub token that can read and edit Gists. The repo-scoped Cloud Agent token may not have that permission. | One GET and one PATCH in the normal path. No direct monetary cost. | Fair. Brian can inspect JSON and revision history in GitHub. | Lowest network-call count. A whole JSON document can be replaced in one PATCH. | The API truncates a file response above 1 MB. Pruning would be required before this queue approached that size. | A PATCH is atomic as one request, but it is not a compare-and-swap. GitHub does not document conditional PATCH for Gists. Two read-modify-write clients can lose one another's changes. |
| SQLite on the Cloud Agent VM | Not reliable across independent scheduled runs. | No service setup, but it only works if all runs share one durable disk. ### Why SQLite is out

Cursor documents the runtime workspace as recycled after a run goes idle.
Snapshots can resume the same agent for up to 90 days, but new agents and
automations start from an environment Build. A Build is a prepared base image,
not a shared writable volume. The local install script also copies skills onto
each VM at startup. A SQLite file might survive a follow-up prompt on one agent,
but there is no guarantee that tomorrow's scheduled agent sees it.

That is not durable state for this use case.

### Why not a Gist

The low call count is attractive, but two details rule it out here:

1. GitHub calls an unlisted Gist "secret", not private. Anyone with its URL can
   read it. This schema contains Slack excerpts and channel metadata.
2. Gist updates do not provide documented optimistic concurrency control.
   Revision history helps recovery after a lost update; it does not prevent one.

Slack List writes are slower, but the data stays under the same workspace access
controls as the source messages. Scheduled runs update only observation fields.
Clear commands update only clear fields. Those writes can overlap without
reopening a cleared item.

## Scope and invariants

- The permalink is the logical primary key.
- The Slack List record ID is the physical row identifier.
- At most one live row may hold a given permalink.
- `cleared` is monotonic. Search observation never changes it back to `open`.
- `snoozed` becomes `open` only when its snooze expires and the original message
  is still present in the fresh search.
- State writes happen only after the digest DM succeeds.
- The daily digest does not repeat every open row. State-level upsert alone
  would not fix the reported problem.
- The skill never adds or removes a reaction.

## Slack List schema

Slack date fields hold dates, not full timestamps. Store timestamps as text so
the skill keeps Slack's decimal message timestamps and full ISO 8601 instants.
Use `-` for an unset text field and `0` for an unset number. This lets the skill
reuse an expired row without sending null values, which the update tool rejects.

| Column | Type | Required | Meaning |
|---|---|---:|---|
| `Permalink` | text | yes | Logical primary key and first column |
| `Channel Name` | text | yes | Rendered channel name or DM participant label |
| `Channel ID` | text | yes | Slack channel, DM, or group-DM ID |
| `Author` | text | yes | Best available author display name |
| `Text Excerpt` | rich_text | yes | Cleaned excerpt, capped at 200 characters |
| `Original TS` | text | yes | Original Slack message timestamp |
| `First Seen TS` | text | yes | ISO 8601 instant when `eyes` first observed the item |
| `Last Seen TS` | text | yes | ISO 8601 instant of the latest successful search observation |
| `State` | select | yes | `open`, `cleared`, or `snoozed` |
| `Snoozed Until TS` | text | yes | ISO 8601 instant, or `-` |
| `Class` | select | yes | `pr`, `doc`, `article`, `thread`, or `msg` |
| `Age At First Seen Days` | number | yes | Whole days between `Original TS` and `First Seen TS` |
| `Last Digest Message TS` | text | yes | Digest DM timestamp, or `-` if never shown |
| `Last Digest Rank` | number | yes | One-based rank in that digest, or `0` |
| `Digest Channel ID` | text | yes | DM channel needed for any later reaction polling, or `-` |
| `Cleared TS` | text | yes | ISO 8601 clear instant, or `-` |
| `Clear Source` | select | yes | `none`, `cursor_clear`, or `eyes_removed` |
| `Write Token` | text | yes | Run UUID that last inserted or recycled the row |

`First Seen TS` never changes during an upsert. `Age At First Seen Days` is
derived once and retained. `Last Seen TS` changes whenever the fresh search
returns the item, including when its state is `cleared`.

### State transitions

| Current state | Event | Next state |
|---|---|---|
| no row | fresh search result | `open` |
| `open` | observed again | `open` |
| `open` | `/eyes clear <rank>` | `cleared` |
| `open` | `/eyes snooze <rank> <until>` | `snoozed` |
| `snoozed` | snooze due and still in search | `open` |
| `snoozed` | explicit clear | `cleared` |
| `open` or `snoozed` | absent from an exhaustive fresh search | `cleared` |
| `cleared` | observed again | `cleared` |

Reopening is explicit. A future `/eyes reopen <permalink>` command may move a
row from `cleared` to `open`. v0.2 search merge does not do it automatically
because the search result cannot distinguish a reaction that remained in place
from one Brian removed and later added again.

## List creation example

This is a deploy-time example. Do not create the list during design work.

```yaml
tool: Slack.slack_create_list
args:
  name: Eyes queue state
  description: Durable state for the private eyes reading queue. Do not share.
  columns:
    - {name: Permalink, type: text}
    - {name: Channel Name, type: text}
    - {name: Channel ID, type: text}
    - {name: Author, type: text}
    - {name: Text Excerpt, type: rich_text}
    - {name: Original TS, type: text}
    - {name: First Seen TS, type: text}
    - {name: Last Seen TS, type: text}
    - name: State
      type: select
      options:
        choices: [open, cleared, snoozed]
    - {name: Snoozed Until TS, type: text}
    - name: Class
      type: select
      options:
        choices: [pr, doc, article, thread, msg]
    - {name: Age At First Seen Days, type: number}
    - {name: Last Digest Message TS, type: text}
    - {name: Last Digest Rank, type: number}
    - {name: Digest Channel ID, type: text}
    - {name: Cleared TS, type: text}
    - name: Clear Source
      type: select
      options:
        choices: [none, cursor_clear, eyes_removed]
    - {name: Write Token, type: text}
```

Save the returned list ID in the deployed `SKILL.md`. Never resolve this list by
its fuzzy title during a normal run.

Example read:

```yaml
tool: Slack.slack_read_list
args:
  list_id: "<EYES_LIST_ID>"
  format: csv
  limit: 100
  cursor: "<omit on first page; pass next_cursor unchanged thereafter>"
```

Example insert:

```yaml

  list_id: "<EYES_LIST_ID>"

    Snoozed Until TS: "-"
    Class: "doc"
    Age At First Seen Days: 2
    Last Digest Message TS: "1789300800.000200"
    Last Digest Rank: 1
    Digest Channel ID: "D123"
    Cleared TS: "-"
    Clear Source: "none"
    Write Token: "<run-uuid>"
```

Example observation update:

```yaml
tool: Slack.slack_update_list_record
args:
  list_id: "<EYES_LIST_ID>"
  record_id: "<Rec...>"
  updated_columns:
    Last Seen TS: "2026-09-14T12:00:00Z"
```

The scheduled path must not include `State` in that update. A concurrent clear
may have changed it after the initial read.

## Read and merge flow

### 1. Load state

1. Read every list page with `limit: 100`.
2. Reject a malformed schema before sending a digest. If a permalink has more
   than one row, use the oldest row as canonical and queue the others for
   reconciliation.
3. Build these indexes:
   - `by_permalink`
   - `recent_open`, where `State=open` and `Original TS` is in the last 7 days
   - `due_snoozed`, where the snooze has expired
   - `last_digest`, selected by the greatest `Last Digest Message TS`
   - `recyclable`, where `Original TS` is outside the window and the row is not
     part of `last_digest`
4. Cap the physical list at 250 rows. Reuse `recyclable` rows before adding new
   rows. This keeps reads to three pages or fewer.

The search can observe at most 20 rows per run. Even if each daily result were
different, the 7-day working set would be at most 140 rows. The extra capacity
keeps the most recent digest mapping and leaves room for manual runs.

### 2. Search Slack

Run the existing `hasmy::eyes: after:<date>` search with limit 20. Create
`fresh_by_permalink` from the response.

### 3. Merge

For each fresh result:

- No matching row: prepare a new `open` row. Set both seen timestamps to now.
- Existing `open`: retain `First Seen TS`; prepare a partial update to
  `Last Seen TS` and changed metadata.
- Existing `snoozed`, not due: update `Last Seen TS`; do not digest it.
- Existing `snoozed`, due: move it to `open` after confirming it is in the
  fresh result set. It is eligible for the digest.
- Existing `cleared`: update `Last Seen TS` only. Do not reopen or digest it.

Do not infer reaction removal when the search returns exactly 20 items. The
result may be truncated. When it returns fewer than 20, treat the result as
exhaustive for the 7-day query. Recent `open` or `snoozed` rows absent from that
result can move to `cleared` with `Clear Source=eyes_removed`.

## Digest dedup policy

Upserting rows without an eligibility rule would still print the same 20 items
every morning. The daily default includes:

- new rows that have no `Last Digest Message TS`
- due snoozed rows that are present in the fresh search
- rows whose previous digest write failed, so they still have no digest marker

It excludes previously digested `open` rows. The footer reports their count:

```text
_14 previously seen items remain open. Run /eyes --all to review them._
```

`/eyes --all` is the escape hatch. It includes all recent `open` rows, still
capped at 20, without changing clear state.

This split is deliberate. Daily runs stop repeating the queue. Manual full
reviews retain the aging behavior requested for v0.2.

## Ranking

Rank every eligible set with this key:

1. Longest awareness age first: `now - First Seen TS`, descending.
2. `pr` and `doc` before other classes.
3. Original Slack age over 5 days, older first.
4. Channels starting with `client-` or `project-`.
5. Newest `Original TS` as the final tie-breaker.

Awareness age is the primary signal. A six-day-old message first discovered
today is less rotten than a two-day-old message that has been on the queue for
two days.

Render each item with queue age:

```text
1. [doc] `#project-ai-gateway` · Example Person · 4d on your list
```

Use whole elapsed days. A newly observed item renders as `0d on your list`.
Slack age can remain available only as a secondary detail if needed.

## Write flow

1. Compose the digest from the merged in-memory state.
2. DM only `U0A0T8FV12B`.
3. If the DM fails, write no state. The next run may retry the same items.
4. Capture the returned digest message timestamp and DM channel ID.
5. Build one write phase for every fresh search result:
   - add a row or fully replace one recyclable row for a new item
   - update `Last Seen TS` for an existing item
   - update digest timestamp, channel, and rank only for displayed items
   - apply safe reaction-removal clears only when the search was exhaustive
6. Run at most four independent record writes concurrently.
7. Retry failed updates once. Before retrying an insert, re-read and check the
   permalink so a timeout does not create a duplicate.
8. If any row still fails, DM one error line naming the count. Do not resend the
   digest in the same run.

The Slack tools do not expose a batch upsert or transaction. "Write phase" means
the skill groups these operations after a successful DM. It does not mean all
rows commit together.

### Concurrent runs

Use narrow updates:

- Scheduled observation updates change observation and digest columns only.
- A clear command changes `State`, `Cleared TS`, and `Clear Source` only.
- A snooze command changes `State` and `Snoozed Until TS` only.

This prevents the common lost-update case. The scheduled run cannot reopen a
row that a manual command cleared while the schedule was running.

Concurrent inserts remain a race because Slack Lists do not enforce unique
values. After any add or row recycle, re-read the touched pages and verify that
each permalink has one row with the current `Write Token`. If two rows share a
permalink, retain the oldest row and mark the other `cleared`. Never include a
duplicate in a digest.

## Clear flow

### Primary: explicit Cursor invocation

Use the existing skill with a command mode. A separate installed skill is not
needed.

```text
/eyes clear 3
```

The command:

1. Reads the list.
2. Finds the greatest `Last Digest Message TS`.
3. Resolves rank 3 within that digest.
4. Partially updates that row to `State=cleared`, `Cleared TS=now`, and
   `Clear Source=cursor_clear`.
5. Confirms the permalink and excerpt in Cursor.

This works without a Slack webhook and identifies one item exactly. It also
works while the `:eyes:` reaction remains on the original message.

### Fallback: original `:eyes:` removal

If Brian removes his `:eyes:` reaction, an exhaustive next search will not
return that permalink. The next scheduled run marks it cleared with
`Clear Source=eyes_removed`.

If the search returns the 20-item cap, absence is ambiguous. Leave the row
unchanged rather than clearing an item that may be below the search cutoff.

### Why digest reactions are not primary

One reaction on one digest message identifies the digest, not a numbered line
inside it. Reacting with `:x:` or `:done:` cannot tell the skill whether Brian
meant item 3 or item 13.

Reaction clearing would require one Slack message per item or a documented set
of rank-specific emoji. Both add UI and API cost, and neither fixes the missing
real-time webhook. Keep `Digest Channel ID` and `Last Digest Message TS` in the
schema so polling with `slack_get_reactions` can be tested later without a
migration.

## Failure behavior

- Missing list tools: DM `eyes: cannot run, missing <tool>` and exit.
- Missing or unreadable list: DM `eyes: cannot read durable state` and exit.
  Do not fall back to stateless v0.1 because that restores the repeat bug.
- Schema mismatch: DM `eyes: state schema mismatch` and exit.
- List disabled with `feature_not_enabled`: report it once and stop. Do not
  create a replacement store automatically.
- Partial post-DM write failure: keep successful rows, retry failed rows once,
  then report the count.
- Duplicate permalink: suppress all but the oldest row from the digest and
  reconcile after the DM.

## Cost envelope

Normal daily run with 20 existing items and no new digest entries:

- Slack search: 1 call
- Slack List read: 1 to 3 calls
- Digest DM: 1 call
- Row updates: up to 20 calls
- LLM: 0 tokens

The run will exceed the v0.1 five-second target in some cases. Set the v0.2
budget only after a deploy smoke test measures List latency. Do not preserve a
five-second claim that the API shape cannot support.

## Deploy checklist

- Create the list as private. Do not share it to a channel.
- Verify Slack Lists are enabled for the workspace.
- Record the exact list ID in `SKILL.md`.
- Add `slack_read_list`, `slack_add_list_record`, and
  `slack_update_list_record` to v0.2 preflight.
- Seed with no rows. Let the first successful digest populate it.
- Run the schedule and a manual `/eyes --all` concurrently in staging.
- Verify a concurrent `/eyes clear 1` stays cleared after the scheduled write.
- Verify an API timeout during insert does not leave duplicate permalinks.
- Verify the default second run does not repeat first-run items.
- Verify `/eyes --all` ranks by `First Seen TS` and renders
  `Xd on your list`.
